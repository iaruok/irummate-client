# 0009. 약관 동의 단계를 서버 동의 기록으로 판정함

- 날짜: 2026-11-28
- 단계: 3단계 (가입 흐름·MY)
- 상태: 결정됨 (0004 결정 2를 대체)
- 결정한 사람: iaruok (인증 코드 변경이라 uukdo 승인 필요)
- 관련: 0004 결정 2(약관 동의 임시 규칙)

## 배경

0004를 정할 때는 서버에 약관 동의를 저장하는 API가 없었다. 그래서 임시 규칙을 두었다. 기본 정보를 냈으면(`detailsCompleted`) 동의한 것으로 보고, 그 전에는 이번 실행 중 동의를 눌렀는지를 메모리에만 기억했다. 이 방식에서는 기본 정보를 입력하기 전에 앱을 껐다 켜면 약관 화면이 한 번 더 나온다.

2학기 서버 `test` 브랜치에 동의 API가 생겼다(서버 커밋 `8d2122c`, 2026-11-22).

| API | 하는 일 |
| --- | --- |
| `GET /api/privacy/consents/me` | 동의 2종(`PROFILE_COLLECTION` 필수, `AI_CERT_TRAINING` 선택)의 상태·동의 버전·현재 버전 |
| `POST /api/privacy/consents/onboarding` | 가입 동의 1회 제출 |
| `PUT /api/privacy/consents/AI_CERT_TRAINING` | 선택 동의 변경 |

서버는 필수 동의(`PROFILE_COLLECTION`)가 현재 버전으로 `AGREED`가 아니면 기본 정보 제출(`POST /api/users/details`)을 403 `PROFILE_CONSENT_REQUIRED`로 거절한다. 인증 상태 응답(`GET /api/auth/status`)에는 동의 필드가 없다.

## 결정

1. **약관 단계는 서버 동의 기록으로 판정한다.** 필수 동의가 `AGREED`이고 동의한 문서 버전이 서버의 현재 버전과 같으면 동의로 본다. 서버가 기본 정보 제출 전에 확인하는 조건과 같다(`features/auth/model/profileConsent.ts`).
2. **동의 기록은 기본 정보를 내기 전에만 묻는다.** 앱 시작과 세션 재확인 때, 인증 상태 응답의 `detailsCompleted`가 false일 때만 `GET /api/privacy/consents/me`를 한 번 더 부른다. 기본 정보를 냈다면 서버가 이미 동의를 확인했으므로 동의로 본다. 가입을 마친 사용자는 지금처럼 요청 하나로 시작한다.
3. **메모리에 두던 동의 표시(`termsProgress`)를 지운다.** 단계 판정의 기기 입력은 소개 완료 표시(`introProgress`) 하나만 남는다.
4. 인증 상태 응답에 동의 필드를 추가해 달라는 0004의 백엔드 요청은 거둔다. 위 2번으로 충분하다.

## 영향

- 기본 정보 입력 전에 앱을 껐다 켜도 약관 화면이 다시 나오지 않는다.
- 동의 기록 조회가 서버 오류·연결 끊김으로 실패하면 인증 상태 조회 실패와 같이 처리한다(비로그인으로 보내지 않고 다시 시도를 기다림).
- 계약 파일(`features/auth/index.ts`)과 세션 타입(`SessionUser`)은 바뀌지 않는다.
- MSW: 인증 상태 응답에 미리 보내던 `termsAgreed`를 지우고, `handlers/terms.ts`가 시나리오에 맞는 동의 기록을 준다. `?session=onboarding&stage=terms`만 미동의이고 그 뒤 단계는 필수 동의를 낸 상태다.

## 남은 것

- **기존 가입자의 재동의:** 필수 동의 문서가 개정돼 현재 버전이 바뀌어도, 기본 정보를 낸 사용자에게는 동의 기록을 묻지 않으므로 약관 화면이 다시 나오지 않는다. 서버에도 아직 필수 동의를 다시 받는 경로가 없다(백엔드에 요청함). 그 경로가 생기면 이 결정의 2번을 다시 본다.
